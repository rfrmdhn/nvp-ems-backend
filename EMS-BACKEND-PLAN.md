# EMS Backend — Development Plan

Single source of truth for the Employee Management System (EMS) backend, built for the
technical-test brief for PT Nusantara Digital. Everything else in this repo (CLAUDE.md,
docs/superpowers/*, actual code) derives from this document. Section numbers (`§N`) are
referenced elsewhere — do not renumber sections without updating those references.

## §1. Overview

EMS backend is a Node.js/NestJS API that lets one seeded admin user log in and manage an
`Employee` roster (CRUD), including bulk-importing employees from a CSV file of 20,000+ rows.
Every employee creation (single or via CSV) is processed asynchronously through a BullMQ/Redis
queue; a background worker process consumes jobs and, on completion, pushes a realtime
notification to the frontend over Server-Sent Events (SSE). The whole stack (Postgres, Redis,
migrations, seed, API, worker) must boot with a single `docker compose up --build`.

This is a technical test, not a production system — scope is deliberately bounded to what the
brief asks for (§9 has the full deliverables checklist), with explicit TODOs for anything pushed
to a later phase (see `docs/superpowers/AUDIT.md` for the ambiguities and
`ASSUMPTIONS_MADE.md` for how they were resolved).

## §2. Stack

- **Runtime**: Node.js 20 (LTS), TypeScript.
- **Framework**: NestJS 11 (modular DI, first-class support for Swagger, class-validator,
  BullMQ, and Passport strategies — the batteries this brief needs are all official Nest
  packages, not community glue).
- **Database**: PostgreSQL 16, accessed via **Prisma ORM** (`@prisma/client` + `prisma` CLI).
  Prisma's migration files are what `migrate deploy` applies at container startup.
- **Queue**: **BullMQ**, backed by Redis 7, via `@nestjs/bullmq`.
- **Realtime transport**: **Server-Sent Events** (Nest's `@Sse()` decorator, RxJS `Subject`
  under the hood) — not Socket.IO, not polling. The only realtime requirement in the brief is
  "worker finishes a job → tell the frontend," which is one-way server→client. SSE is HTTP,
  needs no extra protocol/port, reconnects automatically in every browser via `EventSource`,
  and is materially simpler to implement/operate than a bidirectional WebSocket channel that
  would go unused in the other direction.
- **Auth**: JWT (`@nestjs/jwt`, `passport-jwt`) with bcrypt password hashing.
- **Validation**: `class-validator` / `class-transformer` on all DTOs, wired via a global
  `ValidationPipe`.
- **CSV parsing**: `csv-parse`'s **streaming** API (`csv-parse/lib/index.js` stream interface,
  not `csv-parse/sync`), piped from a `fs.createReadStream`, so a 20k+ row file is never fully
  buffered in memory.
- **API docs**: `@nestjs/swagger`, served at `/api/docs`.
- **Testing**: Jest (Nest's default, generated by `@nestjs/cli new`) — deliberately not
  switched to Vitest; keep Nest's idiomatic tooling.
- **Containerization**: Docker + Docker Compose v2 (`docker compose`, not the legacy
  `docker-compose` binary), cross-platform (Linux/Mac/Windows), named volumes only.

## §3. Data Model

Two Prisma models, defined in `prisma/schema.prisma`:

```prisma
model Admin {
  id           String   @id @default(uuid())
  email        String   @unique
  passwordHash String
  createdAt    DateTime @default(now())
}

model Employee {
  id         String   @id @default(uuid())
  name       String
  age        Int
  position   String
  salary     Decimal  @db.Decimal(14, 2)
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt
}
```

Notes:
- `salary` is `Decimal` (not `Float`) to avoid floating-point rounding on money-like values,
  mapped to Postgres `NUMERIC(14,2)`. The Prisma client returns this as a `Decimal.js` object;
  DTOs/controllers serialize it to a plain number/string for JSON responses.
- No `role` column on `Admin` for now — see §11 / AUDIT.md #1 (single admin role, no distinct
  HR role, is the documented assumption for this phase).
- No persisted `Notification` table in this phase — see AUDIT.md #2. Notifications are
  ephemeral, delivered only to clients connected to the SSE stream at the moment the job
  completes. Documented as a deliberate scope cut, not an oversight.

## §4. Auth

- `POST /auth/login` — public route (no guard). Body: `{ email, password }` (validated via
  `LoginDto` with `class-validator`: `@IsEmail()`, `@IsString() @MinLength(1)`).
- `AuthService.validateAdmin(email, password)` looks up the `Admin` by email, compares the
  supplied password against `passwordHash` with `bcrypt.compare`, throws
  `UnauthorizedException` on either "no such email" or "wrong password" — the API returns the
  same generic `401 Invalid credentials` for both cases, never leaking which one failed.
- On success, `AuthService.login()` signs a JWT (`@nestjs/jwt`) with payload
  `{ sub: admin.id, email: admin.email }`, expiry from `JWT_EXPIRES_IN` (default `1h`), secret
  from `JWT_SECRET`. Response: `{ accessToken, expiresIn }`.
- `JwtStrategy` (passport-jwt) validates the bearer token and attaches
  `{ id, email }` to `req.user`.
- `JwtAuthGuard` (extends `AuthGuard('jwt')`) is applied to every Employees and CSV-import
  route — see §5, §7 — via `@UseGuards(JwtAuthGuard)` at the controller class level, not
  per-method, so a newly-added route can never accidentally ship unguarded.
- A `@CurrentUser()` param decorator (in `src/common/`) reads `req.user` for handlers that need
  the caller's identity (none strictly need it yet, but it's here for the "who triggered this
  action" audit hook a later phase might want).

## §5. Employees CRUD API

All routes under `/employees`, all guarded by `JwtAuthGuard`:

| Method | Path             | Body / Params                         | Behavior |
|--------|------------------|----------------------------------------|----------|
| POST   | `/employees`     | `CreateEmployeeDto` (name, age, position, salary) | Inserts row via Prisma, then enqueues an `employee-created` job with the new employee's id (§6). Returns the created employee (201). |
| GET    | `/employees`     | query: `page`, `limit`, `search`, `sortBy`, `sortOrder` (all optional) | Server-side paginated/searched/sorted list — see §11/AUDIT.md #6 and `docs/superpowers/specs/employees.md` for the exact contract. |
| GET    | `/employees/:id` | `:id` uuid                             | 404 if not found. |
| PUT    | `/employees/:id` | `:id` uuid, `UpdateEmployeeDto` (partial) | Server re-validates `:id` exists before writing; the DTO never carries an `id` field, so a client can never redirect a write to a different row (§ non-negotiable rule in CLAUDE.md). |
| DELETE | `/employees/:id` | `:id` uuid                             | Hard delete (no soft-delete requirement in the brief for this entity). 404 if not found. |

- `CreateEmployeeDto` / `UpdateEmployeeDto` validate: `name` non-empty string, `age` positive
  int (`@IsInt() @Min(16) @Max(100)` — plausible working-age bounds), `position` non-empty
  string, `salary` positive number (`@IsNumber() @Min(0)`).
- `:id` route params are validated as UUIDs via `ParseUUIDPipe`; a malformed id short-circuits
  with `400` before touching Prisma.
- `EmployeesService` is Prisma-only data access in this phase (create/findAll/findOne/update/
  remove); the "enqueue a job on create" call is a single method call out to
  `QueueService`/`EmployeeCreatedProducer` (§6) — the service itself has no queue/BullMQ
  knowledge beyond that one call, keeping data access and async side-effects decoupled.

## §6. Queue Architecture

Two BullMQ queues, registered via `@nestjs/bullmq`'s `BullModule.registerQueue(...)` in
`src/queue/queue.module.ts`, both connected to Redis using `REDIS_HOST`/`REDIS_PORT` (and
optional `REDIS_PASSWORD`) from `ConfigService`:

### 6.1 `employee-created` queue

- **Producer**: `EmployeesService.create()` calls `EmployeeCreatedProducer.enqueue(employeeId)`
  after the Prisma insert commits. Job payload: `{ employeeId }`.
- **Consumer**: `EmployeeCreatedProcessor` (`src/queue/processors/employee-created.processor.ts`),
  a `@Processor('employee-created')` class. On `process()`:
  1. (Optional) re-fetch the employee row for a richer notification payload (name, position).
  2. Simulate a short validation/processing delay (a `setTimeout`-based await, a few hundred ms)
     to make the async nature visible in a demo — this stands in for whatever real
     post-creation work (e.g. payroll system sync, welcome email) a production system would do.
  3. Call `NotificationsService.notifyEmployeeCreated(employee)` to push an SSE event to every
     connected client.
  4. Job resolves; BullMQ marks it completed. Failures retry per queue default (3 attempts,
     exponential backoff) — this queue is small/fast so default settings are fine.
- This is implemented **fully** in this phase — it is the concrete end-to-end proof that
  queue → worker → SSE actually works, and it's small enough to not be a scope risk.

### 6.2 `csv-import` queue

- **Producer**: `CsvImportService.enqueueImport(filePath, originalFilename)` after the upload
  controller has streamed the file to disk (§8). Job payload: `{ filePath, originalFilename }`.
- **Consumer**: `CsvImportProcessor` (`src/queue/processors/csv-import.processor.ts`) —
  **fully implemented**: streams the file via `fs.createReadStream` piped through `csv-parse`'s
  streaming API, validates each row, batches valid rows (500/batch) into
  `prisma.employee.createMany({ skipDuplicates: true })`, and reports progress. See §8 for the
  full design and `docs/superpowers/plans/csv-import.md` for the implementation notes.
- Progress reporting (implemented): byte-based (see §8) — the processor calls
  `job.updateProgress({ processed, total, percent, rowsProcessed })` after each batch insert,
  and pushes the same payload as a `csv-import.progress` SSE event via `NotificationsService`.
  The frontend can also poll `GET /csv-import/:jobId/status`, which calls `Queue.getJob(jobId)`
  and returns `{ jobId, state, processed, total, percent, rowsProcessed, imported, skipped,
  errors }` (fields present depend on job state) — BullMQ's own job-progress mechanism is the
  "pollable/streamable" store the brief asks for, no separate progress table needed.

### 6.3 Redis connection

Configured once in `src/config/` and shared by both the `BullModule` registration and any
direct `ioredis` usage, so `REDIS_HOST`/`REDIS_PORT`/`REDIS_PASSWORD` are the only knobs.

## §7. SSE Notifications

- `NotificationsModule` exports `NotificationsService`, which holds an RxJS `Subject<
  NotificationEvent>` (`NotificationEvent = { type: string; data: unknown; timestamp: string }`).
- `NotificationsService.notifyEmployeeCreated(employee)` calls `.next(...)` on the subject with
  `{ type: 'employee.created', data: employee, timestamp: new Date().toISOString() }`. The
  CSV-import processor uses the same mechanism via three more event types:
  `csv-import.progress` (`data: { jobId, processed, total, percent, rowsProcessed }`, emitted
  once per batch flush), `csv-import.completed` (`data: { jobId, imported, skipped, errors }`,
  `errors` capped to the first 20), and `csv-import.failed` (`data: { jobId, error }`) if the job
  throws before it can resolve.
- `NotificationsController` exposes `GET /notifications/stream` with `@Sse('stream')`, returning
  `this.notificationsService.stream$` mapped into Nest's `MessageEvent` shape
  (`{ data: ... }`). This endpoint is intentionally **not** behind `JwtAuthGuard` in this phase
  for demo simplicity (the SSE payload contains no sensitive data beyond what `/employees`
  already exposes to anyone who can reach the API) — see AUDIT.md #4 for the tradeoff and how
  to add token-based auth (e.g. `?token=` query param, since `EventSource` cannot set headers)
  if this needs to be locked down later.
- One process (the `api` process, not the `worker` process) serves the SSE endpoint. The
  `employee-created` processor runs inside the `worker` process. Because BullMQ jobs and the
  SSE subject live in different Node processes, the processor cannot call
  `NotificationsService.notifyEmployeeCreated()` directly in a multi-process deployment — see
  §7.1 for how this is bridged.

### 7.1 Cross-process bridging (worker → api)

The `worker` process (running `EmployeeCreatedProcessor`) and the `api` process (serving the
SSE stream) are separate Node processes per the brief's Docker layout (§10). To get a
job-completion event from one process to the other, the worker publishes on a Redis Pub/Sub
channel (`notifications:employee-created`) instead of calling the in-memory `Subject` directly;
the `api` process subscribes to that channel on startup (`NotificationsService.onModuleInit`)
and forwards each message into its local RxJS `Subject`, which the SSE endpoint is already
observing. This keeps the SSE fan-out (multiple browser tabs hitting one `api` replica) in
memory/RxJS, while cross-process delivery rides on Redis, which is already a hard dependency.
In the current single-`api`-replica Docker Compose setup this is mostly future-proofing; it
also happens to be exactly what's needed to make the demo modeled on separate `api`/`worker`
containers work at all.

## §8. CSV Import Design (streaming + batch insert) — IMPLEMENTED

1. **Upload** (`POST /csv-import/upload`, guarded, `multipart/form-data`, field name `file`):
   `FileInterceptor('file', { storage: diskStorage({ destination: <uploads dir>, filename: ... }) })`
   — Multer writes directly to disk via a stream; the file is never held fully in memory even
   at the HTTP layer. Reject non-`.csv` files (`fileFilter`) and cap size via
   `limits.fileSize` (200 MB) at the interceptor level. Response: `202 Accepted`, `{ jobId }`.
2. **Enqueue**: controller calls `CsvImportService.enqueueImport(file.path, file.originalname)`,
   which adds a job to the `csv-import` queue and returns `{ jobId }` to the client immediately
   (202 Accepted) — the HTTP request does not wait for the import to finish.
3. **Worker processing** (`CsvImportProcessor` — `src/queue/processors/csv-import.processor.ts`):
   - Open `fs.createReadStream(filePath)`, pipe through `csv-parse`'s stream API
     (`{ columns: true, trim: true, skip_empty_lines: true }`) and iterate with
     `for await (const row of parser)` — parses row-by-row without materializing the whole file.
   - Accumulate parsed rows into an in-memory batch array (`BATCH_SIZE = 500`); on reaching the
     batch size, flush via `prisma.employee.createMany({ data: batch, skipDuplicates: true })`
     inside the batch loop, then clear the array. This keeps peak memory bounded to one batch,
     not the whole file, and keeps DB round-trips to `totalRows / 500` instead of one per row.
   - **Progress reporting: byte-based** (chosen over a row-count pre-pass — see
     `docs/superpowers/plans/csv-import.md` for the tradeoff). `fs.statSync(filePath).size` gives
     the total byte count upfront with no extra pass over the file; `fs.ReadStream.bytesRead`
     gives bytes consumed so far. `percent = min(99, floor(bytesRead / totalBytes * 100))` while
     streaming, jumping to `100` only once the job fully resolves. Reported once per batch flush
     (not per row) via `job.updateProgress({ processed, total, percent, rowsProcessed })` *and* as
     a `csv-import.progress` SSE event through `NotificationsService` (§7) — the same
     worker-to-api Redis pub/sub bridge the `employee-created` processor already uses, not a
     second parallel path.
   - Row validation: name non-empty string, age a positive integer, position non-empty string,
     salary a non-negative number (deliberately looser than `CreateEmployeeDto`'s 16-100 age
     band — see AUDIT.md #3). Per AUDIT.md #3, the documented behavior is **skip-and-collect**:
     invalid rows are skipped and their row number + reason recorded into a per-job error list
     (capped at the first 20 entries — `skipped` still counts every bad row accurately), rather
     than failing the entire import for one bad row.
   - On stream end, delete the temp uploaded file, resolve the job with a summary
     `{ imported, skipped, errors }`, and publish a `csv-import.completed` SSE event
     `{ jobId, imported, skipped, errors }`.
   - On any error while streaming/parsing (including the file being missing), delete the temp
     file if present, publish `csv-import.failed` (`{ jobId, error }`), and rethrow so BullMQ
     marks the job failed.
4. **Status endpoint** (`GET /csv-import/:jobId/status`, guarded): looks up the job via
   `Queue.getJob(jobId)`, returns `{ jobId, state, processed?, total?, percent?, rowsProcessed?,
   imported?, skipped?, errors? }` — `state` from `job.getState()`
   (`waiting|active|completed|failed|...`); `processed`/`total`/`percent`/`rowsProcessed` come
   from the last `job.updateProgress()` payload; `imported`/`skipped`/`errors` come from
   `job.returnvalue` once `state === 'completed'`. This is the fallback for a client that missed
   the SSE events (e.g. the page was refreshed mid-import).

## §9. Testing Scope

Per the brief: "minimal unit tests: login, CRUD employee, queue handler." This phase ships
exactly three real Jest unit test files, each with a mocked dependency layer (no real DB/Redis
needed to run `npm test`):

1. `src/auth/auth.service.spec.ts` — mocks `PrismaService`; covers: successful login returns a
   signed token, wrong password throws `UnauthorizedException`, unknown email throws
   `UnauthorizedException`.
2. `src/employees/employees.service.spec.ts` — mocks `PrismaService`; covers: `create` calls
   `prisma.employee.create` and enqueues a job, `findAll`/`findOne` call the right Prisma
   methods, `update`/`remove` throw `NotFoundException` when the row doesn't exist.
3. `src/queue/processors/employee-created.processor.spec.ts` — mocks
   `NotificationsService`/`PrismaService`; covers: processing a job calls
   `NotificationsService.notifyEmployeeCreated` with the expected payload shape.

Beyond the brief's required three, `src/queue/processors/csv-import.processor.spec.ts` was added
once the CSV-import processor was implemented (§8): a small valid CSV batches correctly through a
mocked `prisma.employee.createMany`, invalid rows are skipped-and-collected rather than failing
the job, a 750-row file flushes as two batches (500 + 250) with monotonically increasing
byte-based progress, and a missing source file publishes `csv-import.failed` and rethrows.
`src/employees/employees.service.spec.ts` was also extended to cover the new `search`/`sortBy`/
`sortOrder` query params (§5/AUDIT.md #6).

Broader taxonomy (smoke/functional/contract/integration/regression/load/stress/security/fuzz)
is scoped down deliberately for this technical test — see CLAUDE.md's Testing Strategy section
for which of those are explicitly deferred and why. `test/app.e2e-spec.ts` (Nest's generated
starter e2e test) is kept/adapted as a placeholder for a future real e2e suite, not expanded in
this phase.

## §10. Docker / One-Command Bootstrap

`docker-compose.yml` services, in dependency order:

1. **`postgres`** — `postgres:16-alpine`, env `POSTGRES_USER`/`POSTGRES_PASSWORD`/
   `POSTGRES_DB` from `.env`, data on named volume `pg_data:/var/lib/postgresql/data`,
   healthcheck `pg_isready -U $POSTGRES_USER`.
2. **`redis`** — `redis:7-alpine`, healthcheck `redis-cli ping`.
3. **`migrate`** — built from this repo's `Dockerfile`, `command: sh -c "npx prisma migrate deploy && npx prisma db seed"`,
   `depends_on: { postgres: { condition: service_healthy } }`, `restart: "no"`. One-shot; exits
   0 on success.
4. **`api`** — same image, `command: node dist/main.js`, `depends_on: { migrate: { condition: service_completed_successfully }, redis: { condition: service_healthy } }`,
   publishes `PORT` (default 3000).
5. **`worker`** — same image, `command: node dist/worker.js`, same `depends_on` as `api`, no
   published port.

Running `docker compose up --build` from `backend/` therefore: builds the image once, starts
Postgres+Redis, waits for both healthchecks, runs `migrate` to completion (schema + idempotent
seed), then starts `api` and `worker` — zero manual steps. This is treated as a standing
invariant: any change that adds an env var, a service, or a migration must update
`docker-compose.yml` in the same change (see CLAUDE.md non-negotiable rules).

## §11. Open Decisions / Scope Boundaries

Tracked in detail in `docs/superpowers/AUDIT.md` (questions) and
`docs/superpowers/ASSUMPTIONS_MADE.md` (the resolution actually implemented). Summary:

- Single `Admin` role only, no distinct "HR" role (brief mentions "HR" loosely but specifies
  one seeded admin).
- Notifications are ephemeral (RxJS/Redis pub-sub in flight), not persisted to a DB table.
- CSV import: invalid rows are skipped and reported, not a whole-batch failure.
- SSE stream requires `?token=<jwt>` (via a dedicated `AuthGuard('jwt-sse')` strategy, since
  native `EventSource` can't set an `Authorization` header — see `AUDIT.md` #4, resolved);
  reconnection is handled entirely by the browser's native `EventSource` retry, no server-side
  backpressure/backlog-replay.
- `GET /employees` pagination/search/sort is server-side (AUDIT.md #6) — the frontend never
  fetches the whole roster in one response, mirroring the CSV importer's "never load the whole
  thing at once" principle.
